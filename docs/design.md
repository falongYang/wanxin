# 晚信产品与技术设计

## 产品定位

晚信是面向成年用户的原创角色陪伴产品。首版以中文、移动端 Web 和一个原创角色「林舟」验证核心体验。林舟是一位在海边值夜班的电台主播。用户可以自由改变话题，并把想留下的一段对话保存成经历卡。卡片兼具可回看的内容与续聊入口。

验证假设是用户愿意保存共同经历，并在新鲜期过后主动从某一张卡重新开始对话。首版支持一个角色、多张经历卡、真实文本回复、刷新后恢复、记忆纠正和删除。交付目标是可邀请体验的 MVP。原生上架、多角色市场、语音、付费、推送和跨设备同步放到后续版本。

## 页面与状态

| 页面 | 正常路径 | 状态与规则 |
| --- | --- | --- |
| 角色发现 | 读角色介绍和开场白，点击和林舟聊天 | 首次进入展示成年确认与 AI 说明。已有会话进入原线程 |
| 自由聊天 | 输入文字并发送，角色结合近期消息回复 | 空白输入忽略，最多 1,000 字。等待中限制重复发送。失败保留已提交消息，原位重试 |
| 卡片预览 | 长按或使用消息操作菜单选中一条自己的消息，将该消息及其相邻回复制成草稿 | 标题和正文可编辑。来源的消息标识固定。取消清除草稿 |
| 共同经历 | 按收藏时间倒序浏览多张卡，从指定卡续聊 | 空列表提供返回聊天入口。相同来源重复收藏返回同一张卡。删除需确认 |
| 卡片详情 | 查看来源、修改卡片、删除或续聊 | 续聊带入当前卡片版本。删除后从历史列表移除，后续提示构造跳过该卡 |
| 会话菜单 | 删除聊天记录和经历卡 | 双重确认后清除当前访问身份的数据，回到首次状态 |

## 数据模型及接口

推荐使用 TypeScript、React、Vite、Node HTTP 服务和 SQLite。浏览器与服务器同源。服务端用随机访客标识及 HttpOnly Cookie 隔离试用数据，浏览器可恢复同一访问身份。部署使用持久卷与 HTTPS，模型密钥仅存服务端环境变量。首轮面向受邀用户，成年自报只用于试用入口，公开发布前需要按目标市场评估适用要求。

| 对象 | 最小字段 |
| --- | --- |
| 访客 | id、adultConfirmedAt、createdAt |
| 线程 | id、visitorId、characterId、createdAt |
| 消息 | id、threadId、role、content、requestId、status、sourceCardId、createdAt |
| 卡片 | id、threadId、sourceMessageId、title、body、createdAt、updatedAt |

- `GET /api/session` 返回当前访客的角色与线程概要。成年确认后初始化线程和固定开场。
- `GET /api/thread` 恢复消息。`POST /api/messages` 接收 `requestId`、`text`、可选 `sourceCardId`，返回用户消息与回复。相同请求重试复用用户消息。服务异常返回可重试状态。
- `POST /api/card-preview` 接收 `sourceMessageId`，返回标题和摘要草稿。生成异常时可重试或用原文手动保存。
- `GET /api/cards` 列表。`POST /api/cards` 收藏。`PATCH /api/cards/:id` 修改。`DELETE /api/cards/:id` 删除。数据库对线程和来源消息组合设唯一约束。
- `DELETE /api/session` 删除该访客的数据并清除会话 Cookie。所有读写按当前访客查询。跨访客的资源标识返回 404。

## 对话和记忆

提示词由固定角色设定、最近 12 条已完成消息和用户本次明确选中的一张经历卡组成。接收卡片时再次校验所有权与存在状态。卡片文本作为用户提供的上下文传入。角色标识持续显示为 AI 虚构角色。经历卡摘要沿用原消息中已有的信息，模型补写的内容由用户在收藏前确认。

首版以用户选择的卡片作为可纠正的长期记忆。修改后的标题和正文只在下次续聊时载入最新版本。删除卡片后还要剔除与该卡关联的续聊消息上下文，原始聊天记录可通过清除会话操作删除。服务端给模型调用设置超时、输出上限、访客限流和每日预算；错误日志仅记事件、状态和延迟。

## 验收与指标

- 用手机窄屏走完整流程。发消息、收藏两张不同来源卡、刷新恢复、编辑一张再续聊、删除后确认其上下文失效。
- 执行离线重试、重复请求、空输入、过长输入、跨访客访问、服务重启、清除会话等检查。
- 记录首次发送、预览、收藏、打开卡片、从卡片开始发送与次日回访事件。事件只带匿名试用标识和时间。
- 观察已发送用户的收藏率、收藏用户的次日回看率、卡片打开到发送的转化率。以测试观察为主，样本量不足时保留方向性结论。

## REA 在实现中的用法

如有自有或明确授权的发布包或测试实例，可在第一天短时核对发现页、消息失败重试和卡片状态，把观察结果写成验收用例。实现依照晚信原创交互和素材。若没有合适目标，直接使用本稿作为输入，进度保持可执行。
